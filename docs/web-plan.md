### 降噪方案
- **4bit 不适用**：ORT 的 4bit 算子 `MatMulNBits` 只覆盖 MatMul，而这个模型全是卷积。模型用 fp32，4.8MB，体积本来就不是问题。
- **全分辨率不可行**：x4v3 每输入像素约 2.36 MFLOP，24MP 全分辨率约 56 TFLOP。所以模型跑在 1/4 尺寸图上，原生 x4 输出回到全尺寸（含分块开销约 4.7 TFLOP），亮度细节再从原图回填，按噪声水平软阈值过滤。三档只改阈值：低 0.75、中 1、高 1.5。
- **8 秒对 WebGPU 的要求**：持续约 590 GFLOPS。M1 GPU 标称峰值约 2.6 TFLOPS，即需要约 23% 的利用率，能否做到要实测。
- **画质**（768px 中心裁切，PSNR dB / 高频相关系数，噪声是在 Bayer 域合成的，不是真实高 ISO，只有 2 个场景）：

| Sony 低 | 28.47 / .76 | 29.92 / .79 | 29.62 / .61 | 30.45 / .61 | 29.95 / .56 | 29.19 / .46 |
| Sony 中 | 22.80 / .51 | 24.38 / .59 | 27.04 / .47 | 28.91 / .51 | 28.45 / .47 | 27.72 / .39 |

### 人脸检测与磨皮
- 检测阈值 0.75，高于 YuNet 常用的 0.6。0.6 时 8 个 RAW 样张里出现 4 个误检（吹风机电线 3 个，0.66–0.74；毛绒猴子 1 个，0.70），它们的非皮肤像素也被磨皮。0.75 时这些误检全部消失，但也放弃了 350D 上一张 48px 的真人侧脸（0.69）。这个阈值只基于 9 张图，检出率必须用带标注的数据集复核：把 LFW 解压到 `Fixtures/faces/lfw/` 后运行 `BENCH=faces npx playwright test e2e/phase2.bench.spec.ts`。
- 瑕疵判定取 8 个方向的最小对比度。修复前，法令纹、下颌线、发丝被当成瑕疵，脸部亮度最多被改 41.7 级，改动 ≥15 级的像素有 232 个；修复后是 30.6 级和 14 个，p99 从 16.2 降到 2.4（astronaut 样张，约 95px 的脸，手工标注的特征点）。
- 只在这一张 512px 的人像上目视检查过，24MP 高清人像的磨皮效果未验证，样张里也没有这样的照片。

### DNG 导出评估（结论：不在本阶段实现）
- 降噪结果是去马赛克后的 RGB，无法写回 Bayer 数据，所以只能做 Linear DNG（`PhotometricInterpretation = LinearRaw`）。
- 需要自写 TIFF / DNG 写入，包括 `DNGVersion`、`UniqueCameraModel`、`ColorMatrix1`、`AsShotNeutral` 和 EXIF IFD；另外要让 LibRaw 输出线性数据，并取到相机色彩矩阵。libraw-wasm 是否暴露这些参数还要确认。
- 24MP 16bit 未压缩约 144MB 一张，走下载兜底不现实，需要 `DirectorySink`（只在安全上下文可用）。
- 需求写的是「DNG（保留 RAW 信息）」，处理后的 Linear DNG 已不是原始 RAW 数据，建议和用户确认这种形式是否满足需求，再排进第三或第四阶段。

### 与需求的差异
- 暂停在两张之间生效，正在处理的一张会做完；取消立即生效。
- 导出丢弃 MakerNote，PNG 和 CR3 不写 EXIF。「保留完整 EXIF」只做到标准字段。
- 浏览器不能在源文件旁建 `output` 文件夹：由用户选目录，或走下载。
- 单张处理过程中没有进度事件，24MP 在 WASM 上要等 80 秒以上，第三阶段的进度条需要先补上。

## 已知风险
- 24MP 降噪 ≤8 秒：WASM 实测约 80 秒，只能依赖 WebGPU，必须在 M1 上实测。这是当前最大的风险
- 嵌套 Worker 只在 Chromium 上验证过，Safari 未测；Worker 内的 WebGPU 路径完全没有跑过
- 浏览器单页内存上限：WASM32 堆最多 4GB，需分块推理并及时释放
- 原图（LibRaw 解码，无相机风格曲线）与内嵌 JPEG 预览色调不同，界面以「预览 / 原图（LibRaw）」标签提示
- 大图用 24MP canvas 显示，Safari 的 canvas 内存上限需在 1.5 实测
- 正式部署必须配置 COOP/COEP 响应头，否则退化为单线程
